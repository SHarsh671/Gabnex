# 3. NON-NEGOTIABLE REAL MARKET DATA REQUIREMENT

**Real external market data is mandatory. Fabricated production prices are prohibited.**

The application must integrate with an actual market-data provider through a backend service. Do not create a fake stock market service, hardcode example prices, or populate production holdings with fictional prices merely to make the dashboard look complete.

## Select a suitable provider

Before implementing the integration:

1. Research currently available stock and ETF market-data APIs.
2. Review the provider's official documentation, supported symbols and exchanges, API limits, authentication, pricing, data freshness, and applicable usage terms.
3. Choose a provider that supports the initial asset scope and is practical for a personal portfolio project.
4. Prefer a provider with an accessible free or low-cost tier, but do not assume that free access includes real-time quotes.
5. Document any restrictions, including delayed quotes, end-of-day data, symbol coverage, and request limits.
6. Use the provider's actual supported endpoints and response formats. Do not invent API endpoints or response fields.

Do not commit to a provider solely because its name appears in this specification. Verify its current capabilities first.

## Market-data architecture

Create a clean abstraction, such as:

- `MarketDataProvider` — interface for market-data operations.
- A concrete provider implementation using the selected API.
- `MarketDataService` — coordinates retrieval, validation, persistence, and caching.
- Appropriate DTOs for provider responses.
- A market-price snapshot model recording the asset, price, currency, source, retrieval time, and provider-reported timestamp when available.

Keep the API key on the backend. Never expose it through React, public environment variables, source code, logs, or API responses.

Use configurable connection and response timeouts. Handle rate limits, timeouts, HTTP errors, invalid JSON, missing values, unsupported symbols, and provider outages.

Cache prices where appropriate to reduce API usage. Cache expiry must respect the provider's update frequency and rate limits. Never present a cached price as newly retrieved data.

## Honest pricing behavior

For every displayed market price, expose enough information to identify its freshness and source.

- Display the last successful retrieval time.
- Display the provider's quote timestamp when available.
- Identify whether data is real-time, delayed, or end-of-day only when the provider establishes that status.
- Clearly mark stale data.
- If a price cannot be retrieved, show it as unavailable.
- If no market-data API key has been configured, show a clear setup or unavailable-data message.
- Allow users to view and manage their recorded transactions even when market data is unavailable.
- Do not silently replace failed API results with hardcoded values.
- Do not invent historical prices, chart points, market movements, or daily returns.
- Do not label an old quote as live or real-time.
- Never represent a successful HTTP response as proof of a valid quote; validate the actual payload and price fields.

**A successful fallback is an honest unavailable-data state, not a fake price.**

For automated tests, use mocked provider responses. Clearly isolate test fixtures from production code. Test data may contain sample prices, but those values must never appear as live market data in a deployed application.

## C. Asset search and watchlist

## D. Investment transactions

Support recording and managing:

- Buy transactions.
- Sell transactions.
- Quantity.
- Execution price.
- Transaction fees.
- Transaction date and time.
- Associated portfolio and asset.
- Optional notes.

Users must be able to view, filter, sort, and paginate their transaction history.

Validate all transaction input. Quantities must be positive, prices and fees must follow sensible monetary rules, dates must be valid, and users must own the associated portfolio.

Prevent selling more shares than the user owns under the chosen accounting model. Short selling is out of scope.

Editing or deleting a historical transaction must recalculate affected holdings and profit/loss consistently. Use database transactions where multiple changes must succeed or fail together.

Do not treat the current market price as the historical execution price. A recorded buy or sell must retain its actual user-entered execution price.

## E. Holdings

Derive holdings from the transaction history rather than letting users manually set their share balances.

For each asset, show:

- Ticker and asset name.
- Quantity held.
- Average cost per share.
- Total remaining cost basis.
- Latest available market price.
- Market value.
- Unrealized profit or loss.
- Realized profit or loss where supported by the transaction accounting model.
- Portfolio allocation percentage where the necessary values are available.

Recalculate holdings after a transaction is added, edited, or deleted.

Do not show misleading zero values when the price or cost basis is unknown. Distinguish a genuine zero from unavailable information.

## F. Dashboard and analytics

Build a dashboard with:

- Total portfolio market value, when all required prices are available.
- Total remaining cost basis.
- Unrealized profit/loss.
- Realized profit/loss.
- Overall profit/loss using clearly defined accounting rules.
- Asset allocation chart.
- Portfolio holdings table.
- Recent transactions.
- Watchlist summary.
- Market-data freshness indicators.
- Clear empty states for a new account.
- Loading, error, partial-data, and unavailable-price states.

Only calculate market-value-based totals when the required data is sufficiently complete. If one or more holdings lack usable prices, communicate that the displayed total is incomplete rather than quietly omitting the holdings or substituting made-up values.

## G. Historical performance

Only implement historical performance charts when the chosen provider supplies the required real historical data and the calculations can be performed correctly.

Distinguish between:

- Changes in portfolio market value.
- Realized and unrealized profit/loss.
- Simple return based on a defined cost basis.
- Time-weighted return.
- Money-weighted return.

These metrics are not interchangeable.

Do not calculate time-weighted or money-weighted returns by simply dividing profit by purchase cost. If the application cannot calculate a metric accurately, omit it or label the simpler metric precisely.

A history of portfolio values reconstructed from actual dated holdings, actual transactions, and real historical prices may be shown if the method is sound and limitations are documented.

Do not invent historical snapshots to create a smoother chart.

# 5. FINANCIAL CALCULATION AND ACCOUNTING RULES

Financial correctness is a core engineering requirement.

## Monetary precision

- Use Java `BigDecimal` for monetary calculations.
- Do not use `double` or `float` for financial arithmetic.
- Define a consistent scale and rounding policy.
- Use explicit rounding modes where rounding is required.
- Keep share quantities at an appropriate precision.
- Avoid unnecessary rounding during intermediate calculations.
- Use decimal database types with appropriate precision and scale.

Document the selected conventions.

## Cost-basis method

Use a clearly documented weighted-average-cost method for the initial implementation unless a specific limitation makes another consistent method more appropriate.

Implement and test:

- Buy transactions increasing quantity and cost basis.
- Transaction fees included consistently in purchase cost basis.
- Sell transactions reducing quantity and the corresponding remaining cost basis.
- Sell proceeds net of applicable selling fees.
- Realized profit/loss based on net proceeds and the cost basis of the shares sold.
- Unrealized profit/loss based on available current market value and remaining cost basis.
- Full liquidation of a holding.
- Repeated buys at different prices.
- Partial sells.
- Transactions with fees.
- Editing and deleting earlier transactions.
- Invalid transactions and insufficient holdings.

For weighted-average cost, calculate the remaining average cost according to the documented policy and handle rounding residuals consistently when shares are sold. A fully liquidated holding should not retain an unexplained residual cost basis.

Use a consistent sign convention for profits, losses, and cash flows. Define whether displayed values include fees and explain the policy in the README.

## Allocation

Calculate asset allocation using eligible, available market values and a clearly defined denominator. Do not include unavailable prices as zero without explaining the resulting distortion.

If all required market values are unavailable or the denominator is zero, show an unavailable or empty state rather than dividing by zero.

## Database consistency

- Use database transactions for logically atomic operations.
- Validate data at the application layer and enforce suitable database constraints.
- Prevent duplicate watchlist entries.
- Add indexes for commonly queried foreign keys and filters where justified.
- Use migrations for schema changes.
- Avoid deleting or corrupting related transaction records accidentally.
- Test calculations using explicit expected results, not only tests that assert a result is non-null.
